Current target: beta to 1.0

Plums 1.0 Roadmap

Plums already has a usable core: terminal UI, streaming chat, configurable layouts and commands, sessions, models, skills, tool rendering, questions, and multiple backend providers. The path to 1.0 is mostly about reliability, documentation, configuration safety, and clear provider contracts rather than adding many new widgets.

Usable

Core prompt, stream, session, layout, model, skill, and backend flows exist and are covered by tests.

Not 1.0

Some internals are still prototype-grade: fake agent registry, partial TOML parsing, sparse docs, and mixed provider maturity.

Focus

Stabilize current behavior first. Keep scope small, explicit, configurable, and provider-safe.

1.0 Definition

Recommended 1.0 promise: Plums is a reliable terminal UI for running agent sessions in a project directory, with stable opencode support, documented configuration, predictable sessions, safe terminal behavior, and clear diagnostics when something goes wrong.

Codex can either be promoted to stable after the provider contract is finished, or explicitly marked experimental for 1.0.

Must Finish Before 1.0

1. Replace the fake agent registry

internal/core/registry.go still says it contains temporary fake outputs. For 1.0, agents/modes should be real data, not hardcoded build and plan.

  • Define where agents are configured or discovered.
  • Validate selected mode/agent before sending prompts.
  • Expose descriptions and capabilities in the palette/help UI.
  • Keep provider-specific agent behavior inside provider boundaries where needed.

2. Make provider maturity explicit

The provider abstraction is useful, but provider semantics need to be documented and tested.

  • Document persistence expectations for sessions and messages.
  • Normalize tool, question, model, and session behavior across providers.
  • Move Codex approval policy, sandbox, and model fallback behavior into provider config.
  • Either finish Codex persistence/session behavior or label Codex experimental.

3. Harden config parsing and validation

internal/app/config.go currently parses and rewrites TOML manually. This is acceptable for WIP, but too fragile for a public 1.0 config surface.

  • Use a real TOML parser or formally document the limited supported syntax.
  • Validate config.toml, layout.json, and commands.json before entering the TUI.
  • Append missing persisted keys instead of only updating keys that already exist.
  • Report invalid values clearly instead of silently falling back where correctness matters.

4. Write real user documentation

The README needs to become complete enough for a new user to install, run, configure, and troubleshoot Plums without reading source code.

  • Install and prerequisites with supported versions.
  • Quick start for opencode.
  • Keybindings and submit behavior per layout.
  • Slash commands and command palette actions.
  • Config file locations and precedence.
  • Layout and command config schema examples.
  • Backend selection and provider limitations.
  • Skills discovery and /skill usage.
  • Troubleshooting for missing executables, terminal issues, port conflicts, and invalid config.

5. Add diagnostics

Add a non-interactive health check before 1.0. Users need a way to debug setup problems without entering the full TUI.

  • plums doctor or plums --doctor.
  • Check terminal availability and dimensions.
  • Check opencode and codex executables.
  • Check selected config paths and validate files.
  • Check backend health and derived opencode server URL.
  • Print active backend, model availability, and useful next actions.

Should Finish Before 1.0

6. Add in-app help

Add /help and a palette item that show keybindings, slash commands, current backend, current model, current session, and config paths.

7. Improve user-facing errors

Provider and startup errors should be short, specific, and actionable. Raw internal errors can still go to PLUMS_LOG.

  • Missing executable.
  • Server startup failure.
  • Port conflict.
  • Unsupported terminal.
  • No connected models.
  • Invalid config.
  • Stream interrupted.
  • Question reply failed.

8. Make cancellation explicit

Stream cancellation exists internally during quit, backend switch, and resubmit. Users need a visible cancel behavior.

  • Define Ctrl+C while streaming as cancel generation.
  • Define Ctrl+C while idle as quit.
  • Show this in the status bar/help screen.

9. Terminal compatibility pass

Verify keyboard, mouse, paste, resize, and modified Enter behavior in common terminals and under tmux.

  • Apple Terminal
  • iTerm2
  • Ghostty
  • WezTerm
  • Alacritty
  • Kitty
  • tmux

10. Release process

Make releases boring and repeatable.

  • Document ldflags for version, commit, and build date.
  • Add changelog or release notes policy.
  • Publish binaries or document package manager path.
  • Define semver expectations for config schema version 1.

Could Ship After 1.0

Post-1.0 improvements

  • Themes and more layout presets.
  • Search chat history.
  • Export transcript.
  • Rename/delete sessions if providers support it.
  • Copy last assistant message or code block.
  • Shell completions.
  • Homebrew or Nix packaging.
  • Provider plugin loading.
  • Token/cost display when providers expose it.
  • File/image attachments.

Non-Goals For 1.0

  • Do not add a large plugin system before the core provider contract is stable.
  • Do not add many UI features before docs, config validation, and diagnostics are finished.
  • Do not promise stable Codex behavior unless persistence, policy config, and model/session semantics are settled.
  • Do not support arbitrary custom commands unless command execution semantics and permissions are designed.

Current Verification

As of this roadmap update, the full Go test suite passes with go test ./.... That means the app is not blocked by obvious test failures; the remaining 1.0 work is about product reliability, clarity, and release readiness.
