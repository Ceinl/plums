plums v2 — execution plan

Turning your keep/redo/cut triage into a sequenced, strangler-style rebuild. Every phase leaves a runnable app. Reserved seams (harness, AgentRegistry) are untouched.

1. The direction (what your triage says)

Two kinds of thing only: plugins and options. Anything that is a unit of behaviour — components, layouts, commands, backends, hooks, the palette, sessions, skills, questions, git-diff — is a plugin. Anything that isn't — theme, keybinds, default layout, visibility toggles, widths, clipboard command — is an option in cfg.Opts (a deliberately long list). The kernel ("Core") knows no concrete feature by name.

The app's own defaults are a built-in Default Config: an internal Go package that returns a config.Config using the exact same {Opts, Plugins} shape as an external config — compiled into the binary, not shipped to disk. The external user config is layered on top, last-wins (overrides Opts field-by-field, shadows/Disable plugins by name). The JSON/TOML config path, the hardcoded keymap, and the privileged component factory are deleted — but TOML returns in one narrow role: an app-managed dynamic-preferences store for options opted in via cfg.Dynamic.

Built-ins live in public, forkable plums/plugins/<name> packages; the built-in Default Config (an internal pkg) just lists them — your split-layout note generalized to everything.

3. The config you'll write

Resolved shape (your sketch, made idiomatic): a Config() function returning config.Config{Opts, Plugins}; each plugin is {Self, Opts} and the loader calls Self.Init(host, opts).

package config

import (
    cfg "github.com/Ceinl/plums/config"
    // built-ins are normal packages — import the ones you want, fork any of them
    "github.com/Ceinl/plums/plugins/split"
    "github.com/Ceinl/plums/plugins/opencode"
    "github.com/Ceinl/plums-user/plugins/github"  // your own
)

func Config() cfg.Config {
    return cfg.Config{
        Opts: cfg.Opts{
            Backend:       cfg.Dynamic,        // remembered at runtime in the TOML prefs store
            Model:         cfg.Dynamic,
            DefaultLayout: "split",          // pinned
            HideThinking:  cfg.True,
            Theme:         mytheme.Dark(),     // theme is an OPTION, not a plugin
            Keybinds: []cfg.Keybind{           // keymap is an OPTION too
                {Key: "ctrl+p", Do: "palette.open"},
                {Key: "ctrl+s", Do: "prompt.submit"},
            },
        },
        Plugins: []cfg.Plugin{
            {Self: &split.Plugin{},    Opts: split.Options{LeftWidth: 50}},
            {Self: &opencode.Plugin{}, Opts: opencode.Options{ServerURL: "…"}},
            {Self: &github.Plugin{},   Opts: github.Options{Limit: 20}},
        },
    }
}
Decisions locked: public config + capabilities packages; Opts passed to Init; minimal theme lives in the Default Config's Opts.Theme. Backend-specific settings (e.g. opencode server URL) live in that plugin's Opts, not in global cfg.Opts.

4. Opts — everything that isn't a plugin

Your rule: "everything that is not a plugin has to be an option." cfg.Opts is the catch-all — a long, typed struct. Representative (not exhaustive) fields:

Dynamic preferences (the TOML store)

A field set to cfg.Dynamic is not fixed by config: Core seeds it from a small app-managed TOML state file (e.g. ~/.config/plums/state.toml) at startup, and writes it back when you change it at runtime (switch backend/model/layout in the palette). A fixed value ("opencode") pins it and ignores the store. This is how the app "remembers preferences" without re-introducing user-authored TOML config.

Merge rule (last-wins, top-to-bottom): Core starts from the Default Config's Opts, then overlays the external Opts — explicitly-set fields override, unset fall through. Fields whose zero value is meaningful (bools/ints) use sentinel/optional types (e.g. cfg.True/cfg.False tri-state) so "unset" is unambiguous. Finalised in Phase 0.

5. The capability model (plugins)

Capabilities are for plugins (behaviour). Theme and keybinds are NOT here — they're Opts. Two kinds:

Host services — Core provides, plugins/components consume

CapabilityReplacesConsumed by
Palette — open a list/command pickercm-palette, OpenListany command/component
Clipboard — copy/pastekb-clipcomponents (editor, chat)
Completion — register @file / /slash sourcescm-at, cm-dropdowncomponents opt in to expose completions
Mouse/Selection — drag-select, wheelkb-mousecomponents via optional ifaces

Keybinds (Opts.Keybinds) map keys to command names; the keymap is data the user owns, so plugins register commands, not bindings. Theme (Opts.Theme) is read by components through RenderCtx.Theme().

Optional interfaces — implemented by plugins, discovered by type assertion

  • Component: KeyHandler · MouseHandler · Scrollable · SelectionProvider · DirtyTracker · CompletionProvider (the chat_output pattern, generalized).
  • Backend adapter: Sessions (list/create/clear/reset) · Models (list/select) · Skills (list/load) · Questions (reply). Core backend contract stays minimal (health, send, stream); the rest are optional, so /sessions /model /backend /skills and question prompts become capability-driven plugins.

6. Phases (strangler — app runs after each)

Phase 0 — Public surface, Opts, Default Config, merge foundation

  • Create plums/config (Config, the long Opts incl. Theme+Keybinds, Plugin{Self,Opts}, Config() discovery, cfg.Dynamic/cfg.True/cfg.False sentinels) and plums/capabilities (move today's interfaces + domain types out of plums/plums/layout).
  • Build the Default Config as an internal pkg returning config.Config — same shape, compiled in, lowest priority.
  • Implement the Opts merge (default ← external, last-wins, field-by-field with sentinel tri-state for ambiguous zeros) and the loader (Self.Init(host, opts)).
  • Update internal/build main generator to call config.Config(); auto-build path unchanged.

Exit: compiles & runs identically; new import surface; Default Config drives defaults; external config overrides top-to-bottom; old plums pkg removed.

Phase 1 — Capability services in Core enabler

  • Define + wire host services: Palette, Clipboard, Completion, Mouse (interfaces in capabilities, implementations in Core, handed out via Host/Ctx). Theme + keybinds are Opts, not services.
  • Components read Opts.Theme via RenderCtx.Theme(); Core resolves Opts.Keybinds (key→command) centrally.
  • Built-ins keep working but now route through these services internally.

Exit: capabilities exist and are exercised by current built-ins.

Phase 2 — All components become real plugins cp-* redo · pl-dogfood

  • Port every pane to a public Component (Surface/RenderCtx + optional ifaces), owning its own state: editor, input_box, sessions, status_bar, info_tabs, info_view, command_palette_panel, separators, difflog. (chat_output already done.)
  • Grow RenderCtx read accessors as each pane needs (server status, mode, model, sessions, tabs, diff).
  • Delete pluginComponent, AppComponentFactory, ComponentFactoryProvider, the factory registry. Cut fullscreen_view; decide text.

Exit: every pane is a public component; privileged path gone; --doctor shows all components owned by plugins.

Phase 3 — Layouts → Default Config plugins ly-chat→cut-builtin · ly-zen/narrow redo

  • Move chat, zen, narrow_chat, narrow_split (split already done) into plums/plugins/* as layout plugins; Core keeps only the div engine + layout capability.
  • Cut fullscreen layout. Improve layout switching (ly-switch).

Exit: Core has zero builtin layouts; the Default Config provides the standard set.

Phase 4 — One command system cm-slash · cm-actions redo

  • Reimplement /new /sessions /model /backend /skills /command as plugins using Command.Do + the new capabilities (Palette, Sessions, Models).
  • Palette actions (mode/layout/visibility/output%) become commands.
  • Delete commands.json, PaletteAction enum, legacy trigger command_registry. @/slash completion move to the Completion capability.

Exit: a single command path; no command JSON.

Phase 5 — Keybinds as Opts, kill config-TOML, add dynamic-prefs kb-config · cf-init kb-default · cf-toml

  • Opts.Keybinds (key→command) is the keymap; the Default Config ships the default map as data. Cut the 400-line keyboard.go mega-handler; Core just resolves key→command.
  • Delete TOML/JSON as a user-config format — the compiled config is the only authoring path.
  • Add the dynamic-prefs store: Core reads/writes a small state.toml for Opts fields set to cfg.Dynamic (remembers backend/model/layout/visibility/output%).
  • First run auto-creates the user config (cf-init redo) instead of requiring -init-config.

Exit: no user-authored JSON/TOML; keymap is Opts; runtime prefs persist via the dynamic store; first launch self-seeds.

Phase 6 — Backend-adjacent features as plugins/caps be-switch · be-model · ss-list · sk-skills · qa-questions · ft-gitdiff redo

  • /backend switch and /model select → plugins over the Models/Backend capability.
  • Sessions (list/new/clear/reset) → backend-adapter Sessions capability + a sessions plugin; reset lives in the claude-mirror plugin (ss-reset).
  • Skills → plugin; Questions/permissions → default plugin with the required Questions capability; git-diff → plugin (cp-diff moves with it).

Exit: backends expose optional capabilities; all side-features are plugins.

Phase 7 — Finalise Default Config + tmux plugin kb-tmux cut→plugin in-theme · in-keys

  • Finalise the built-in Default Config (internal pkg): full default Opts — including Opts.Theme (the minimal theme) and the default Opts.Keybinds — plus the bundled plugin list.
  • tmux extended-keys → a tmux/claude-mirror plugin. Expose the keyboard parser for plugins (in-keys).

Exit: App = Core + Default Config, both expressed through the public API; theme & keymap are Opts; total dogfooding; --doctor shows every feature owned by a plugin.

Phase 8 — Streaming UX redo ft-stream parallel workstream

  • Redesign the streaming render ("looks ass") — separate UX track; needs a visual direction pass. Can run alongside Phases 2–7 since chat_output is already a public component.

Exit: streaming render you're happy with.

8. Sequencing notes & risks

  • Order matters: Phase 0–1 (surface + capabilities) must precede the rest — they define the contracts everything else targets.
  • RenderCtx growth: Phase 2 will expand RenderCtx the most; freeze it only once 2–3 stateful panes are ported (status_bar, sessions, editor).
  • Biggest lift: Phase 2 (components) and Phase 4 (commands) are the heavy ones; each is independently shippable.
  • Deletions are the point: keymap mega-switch, commands.json, TOML, factory path, fullscreen — removing them is how the app stops feeling half-finished.
  • Reserved seams (harness/agents/permissions) stay exactly as-is throughout.
