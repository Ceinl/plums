Step 1 — Architecture & extensibility audit

Goal of this step: confirm the architecture matches the plugin-first target in DESIGN.md, and decide — per tool kind — whether a user could recreate it as an external plugin. No code was changed in this step; the deliverable is the map below.

1. Plan for this step

  1. Read the public API floor (plums/), the kernel (internal/kernel), and the wiring hub (internal/api).
  2. Trace the load path: config → kernel.Load → registry → app.Deps → render.
  3. Verify the two hard dependency-direction rules from DESIGN (public API never imports internal/; raw providers never import the port/bridge).
  4. Produce a dependency tree and a per-kind extensibility verdict with the exact seam each plugin author would use.

2. How plums boots (control flow)

A single hub, internal/api.Run, resolves config, loads the kernel, pulls typed entries out of the registry, and hands them to the TUI app as app.Deps.

cmd/plums/main.go  ──►  plums/runtime.Main  ──►  internal/api.Run

internal/api.Run
 ├─ resolveKernelConfig()            // TOML/flags → plums.Settings; or a compiled plums.Use() Config
 ├─ kernel.Load(config, Defaults: builtin.DefaultPlugins)
 │     ├─ activate each default plugin   // core: 1 plugin/backend + components + layouts + commands
 │     ├─ activate config.Plugins()      // user plugins (last-wins over core)
 │     ├─ activate config capabilities   // config itself may add commands/components/…
 │     └─ registry.Disable(settings.Disable)
 ├─ backendRegistrationsFromRegistry() ─► app.BackendRuntimesFromRegistrations()
 ├─ commandsFromRegistry()             ─► []plums.Command
 ├─ layoutsFromRegistry()              ─► []app.LayoutType   // public Node tree → internal layout
 ├─ componentFactoriesFromRegistry()   ─► map[name]ComponentFactory
 └─ app.Run(ctx, Deps{Layouts, Commands, Components, Backends, Hooks, Keybinds})

Every tool the running app uses is pulled from the registry in registration order — there is no hard-coded built-in list consumed past builtin.DefaultPlugins. That is the property that makes overriding real: a user plugin registered later with the same name shadows the default, and plums doctor / --doctor prints the resolved set with provenance.

Dogfooding: built-ins expressed through the public APIPartialBackends, layouts, hooks: yes. Components & commands: not yet — see Step 3. This is the one real gap.

6. Findings carried into later steps

  • Step 2 Dead code exists: ~9 unreachable functions (clipboard, skills, two provider helpers each in opencode/codex, two markdown helpers). Removed in Step 2.
  • Step 3 Component dogfooding gap — the highest-value architectural item. Built-in panes bypass the public Component/RenderCtx contract via ComponentFactoryProvider. The public path is proven only by chat_output. Until a second non-trivial built-in (e.g. status_bar) is ported, RenderCtx completeness is unverified — exactly DESIGN open-question #3.
  • Step 3 Command dual-system — commands.json + PaletteAction enum runs in parallel with public Command.Do. Built-ins should migrate onto Do so there is one path.
  • note internal/core/registry.go (AgentRegistry, fake outputs) and internal/core/harness are reserved seams — correctly excluded from all cleanup.
